# jobsearch (FreeMarker): every reachable template, each form in its empty/invalid and valid states,
# anonymous vs job seeker, and the error pages. Requests run in order against a fresh in-memory H2
# with the app's Liquibase seed data (users 1-3, vacancies 1-32, resumes 1-33, responses 1-34).
# Registration logs the new user in, so the job seeker registered below is user 4; her resume is 34
# and her response to vacancy 1 is 35.
#
# Left out on purpose:
# - The employer role. The app cannot create an employer: registering with "Employer" gives the
#   JOB_SEEKER role (UserMapper wants "EMPLOYER") and "EMPLOYER" fails the role lookup. The seeded
#   employer's password is unknown. Employer-only pages show only as a 403 (last request below).
#   The vacancy and resume-list templates are still reached through routes that are not restricted
#   to employers (/skills/new_vacancy, /skills/update_vacancy, POST /vacancies/..., /resumes/sort).
# - Anything that calls out: POST /auth/forgot_password for a real user (SMTP), skill search or
#   adding skills (api.hh.ru), Google login.
# - Multipart uploads (group image, video, avatar, chat file), so there is no group or video to view.
# - Pages the app itself crashes on mid-render (the crawl gets a truncated response):
#   validation_error.ftlh, an empty chat message, GET /skills/new_resume and /skills/update_resume.
# - Skill POSTs: the empty skills page has no form, so no CSRF token to send.
# - GET /users/update/profile: its hidden password field holds the bcrypt hash, which changes on
#   every run. The invalid POST shows the same template.
# - Paged vacancy lists. The seed gives all 32 vacancies the same timestamp and the lists sort by
#   date (or salary, with ties), and H2's LIMIT sort orders ties at random, so a page of 10 or 20
#   holds a different subset each run. Lists are fetched with size=50 to show every vacancy; their
#   order can still change between runs, which scoring accepts as "reordered".
